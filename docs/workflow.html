🗄️ MariaDB Operator Playbook

Click any step to expand its plain-English explanation

1
Safety Check pre-task

What: Before doing anything, verify that the database root password has been provided.

Why: Deploying a database without a password would leave it wide open. This guard stops the process immediately with a clear error message.

💡 Analogy: Like a pilot's checklist — confirm fuel is loaded before taxiing to the runway.
✔ Password OK
✖ Missing → STOP
2
Add Helm Repository task

What: Register the Presslabs chart repository with Helm.

Why: Helm needs to know the URL of the "app store" where the MariaDB Operator package lives before it can download anything.

💡 Analogy: Adding a new app store to your phone so you can download a specific app.
3
Create Namespace task

What: Create a dedicated area called mariadb-operator inside the Kubernetes cluster.

Why: Namespaces keep resources organised and isolated. The Operator's pods, secrets, and services live here — separate from everything else.

💡 Analogy: Creating a new folder on your computer to keep project files in one place.
4
Store Root Password task

What: Save the MariaDB root password as an encrypted Kubernetes Secret inside the cluster.

Why: Passwords should never be stored in plain text. Kubernetes Secrets are access-controlled — only authorised pods can read them.

This step is skipped during uninstall (state: absent).

💡 Analogy: Putting a house key inside a locked key-safe that only approved family members know the combination to.
5
Install / Upgrade Operator task

What: Use Helm to deploy (or upgrade) the MariaDB Operator into the cluster. The playbook waits up to 10 minutes for the deployment to become healthy.

Why: This is the core step — it installs the software that will manage databases on your behalf. Pinning a specific chart version ensures repeatability.

💡 Analogy: Installing an app from the store and waiting for the "Installation complete" confirmation.
6
Wait for Readiness handler

What: After all tasks finish, check that the Operator Deployment has the correct number of healthy replicas.

Why: This handler only fires when Step 5 made a change. On repeat runs where nothing changed it is skipped — saving time.

How: Ansible polls the Deployment's status.availableReplicas until it equals 1 (or the configured count), or until the 10-minute timeout is reached.

💡 Analogy: After plugging in a new appliance, checking the indicator light turns green before walking away.
